# lib-log-core

Reusable logging abstraction for Java enterprise applications.

This library provides standardized logging contracts, contextual logging
support, SLF4J-based implementations, and common observability field names.

It is designed to provide applications with a consistent logging API while
keeping business and application code independent from a specific logging
backend.

## Features

- Standardized logging contract
- Debug, info, warning, and error log levels
- Structured logging attributes
- Exception logging
- Contextual logging support
- SLF4J integration
- SLF4J MDC context management
- Correlation ID support
- Distributed tracing field support
- Standardized observability field names
- Logger factory abstraction
- No Spring dependency
- No logging backend imposed on consuming applications

## Core Concepts

### LogService

`LogService` defines the main logging contract exposed by the library.

Supported log levels include:

```text
DEBUG
INFO
WARN
ERROR
```

Logging operations use:

```text
event
message
context
attributes
throwable
```

depending on the selected operation.

An explicit event identifier allows applications to use stable,
machine-searchable event names independently from human-readable messages.

## Structured Logging

The library supports additional structured attributes for informational log
events.

Typical attributes may include:

```text
purchaseId
customerId
merchantId
amount
currency
status
```

Structured attributes should describe relevant event information without
placing application business logic inside the logging library.

## Logging Context

`LogContextHolder` defines an abstraction for values associated with the
current logging execution context.

Typical contextual values include:

```text
correlationId
traceId
spanId
application
environment
operation
status
durationMs
```

Contextual information allows logs generated by different components of the
same execution flow to be correlated and analyzed consistently.

## MDC Integration

`MdcLogContextHolder` implements `LogContextHolder` using SLF4J MDC.

The MDC context can be used to propagate information associated with the
current execution flow, such as:

```text
Correlation identifiers
Tracing identifiers
Application information
Execution environment
Operation metadata
```

Null keys and values passed to the context holder are ignored.

Applications should clear request-specific MDC values when the execution
context finishes to prevent values from leaking into subsequent executions.

## Standard Log Fields

`LogFields` centralizes the names of commonly used logging and observability
fields.

Current fields include:

```text
correlationId
traceId
spanId
application
environment
event
operation
status
durationMs
```

Using common names across services helps maintain consistency when logs are
indexed, searched, correlated, or analyzed by observability platforms.

## SLF4J Implementation

`Slf4jLogService` is the default implementation of `LogService`.

It delegates log emission to SLF4J and enriches each log entry with contextual
values obtained from a `LogContextHolder`.

The generated log structure follows the conceptual format:

```text
event
message
context
attributes
```

Error logs may additionally include an associated exception.

Only non-null and non-blank context values are included in the contextual
information generated by the service.

## Logger Factory

`LogServiceFactory` defines the abstraction for obtaining a `LogService`
associated with a source class.

`Slf4jLogServiceFactory` provides the SLF4J-based implementation and shares
the configured `LogContextHolder` with created logger instances.

Conceptually:

```text
Application Class
       │
       ▼
LogServiceFactory
       │
       ▼
Slf4jLogService
       │
       ▼
     SLF4J
```

## Architectural Position

```text
┌───────────────────────────────┐
│     Consuming Application     │
├───────────────────────────────┤
│          LogService           │
│     LogServiceFactory         │
├───────────────────────────────┤
│      Slf4jLogService          │
│ Slf4jLogServiceFactory        │
├───────────────────────────────┤
│      LogContextHolder         │
│    MdcLogContextHolder        │
├───────────────────────────────┤
│            SLF4J              │
├───────────────────────────────┤
│ Logging Backend / Runtime     │
└───────────────────────────────┘
```

Application code should depend primarily on the contracts exposed by the
library rather than directly depending on a concrete logging implementation.

## Design Principles

This library follows these principles:

- Provide a consistent logging abstraction across applications.
- Keep application code independent from concrete logging backends.
- Use stable event identifiers for searchable application events.
- Keep human-readable messages separate from event identifiers.
- Support structured logging information.
- Support correlation and distributed tracing metadata.
- Centralize common observability field names.
- Avoid business logic inside logging infrastructure.
- Avoid static application-level logging utilities.
- Prefer explicit dependencies through constructors or factories.
- Keep logging infrastructure independent from Spring.
- Delegate actual log delivery to the configured SLF4J backend.

## Framework Independence

`lib-log-core` does not require Spring or Spring Boot.

The library depends on SLF4J as its logging abstraction but does not require
application components such as:

```text
Spring Framework
Spring Boot
JPA
Hibernate ORM
Servlet APIs
Database drivers
Cloud SDKs
```

The consuming application is responsible for providing an SLF4J-compatible
logging backend at runtime.

Examples include:

```text
Logback
Log4j2 through SLF4J
Other SLF4J-compatible providers
```

## Observability Integration

The standard fields exposed by this library can be used by centralized
observability platforms.

Typical integrations may include:

```text
Elastic Stack
Grafana Loki
Azure Monitor
Application Insights
Splunk
Datadog
OpenTelemetry-based platforms
```

The library itself does not depend on any of these platforms.

## Context Lifecycle

Context values usually belong to an individual execution flow.

A typical lifecycle is:

```text
Execution starts
      │
      ▼
Context values are added
      │
      ▼
Application operations execute
      │
      ▼
Logs include contextual information
      │
      ▼
Context is cleared
```

Consumers are responsible for defining the appropriate lifecycle according to
their execution model.

## Sensitive Information

Logging infrastructure should not be used to expose sensitive information.

Applications should avoid logging values such as:

```text
Passwords
Encryption keys
Authentication tokens
Full payment card numbers
Security codes
Sensitive personal information
```

Sensitive values should be removed, masked, or otherwise protected before
being supplied to the logging API.

## Runtime Logging Backend

`lib-log-core` should depend on the SLF4J API rather than imposing a concrete
logging backend.

The consuming application should provide its preferred SLF4J implementation.

For example, a Spring Boot application normally obtains its logging backend
from the application's existing logging configuration.

## Testing

Unit tests cover the behavior of:

```text
MdcLogContextHolder
Slf4jLogService
Slf4jLogServiceFactory
```

The test suite verifies:

- MDC value storage
- MDC value retrieval
- Context value removal
- Context cleanup
- Null context handling
- Logger creation
- Debug logging
- Info logging
- Warning logging
- Error logging
- Exception logging
- Structured attributes
- Context enrichment
- Null context value exclusion
- Blank context value exclusion

A concrete logging implementation such as Logback can be used exclusively in
test scope to capture and inspect generated SLF4J events.

## Test Dependencies

Logback may be declared as a test-only dependency:

```xml
<dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>${logback.version}</version>
    <scope>test</scope>
</dependency>
```

Keeping Logback in test scope prevents `lib-log-core` from forcing a logging
backend on consuming applications.
